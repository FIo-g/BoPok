## 1. 왜 만드는가

부모님과 여행을 가면 일정은 자녀가 짜고 부모님 의견은 잘 들어가지 않는 경우가 많다. 그러다 막상 관광지에 도착해서 2시간을 걸어야 하거나, 거동이 불편하신데 계단으로만 갈 수 있는 길을 만난다.

보폭은 이런 일을 **여행 전에** 막는다. 관광지마다 계단·쉼터가 어디 있는지, 걸어서 얼마나 걸리는지를 보여주고, 그 정보를 바탕으로 가족이 함께 의견을 내며 일정을 고친다. 목표는 "부모님이 좋아하실 곳을 맞히는 것"이 아니라 **부모님이 큰 불편이나 불만 없이 만족스럽게 다녀오시는 것**이다.

서비스의 핵심은 두 가지다.

1. **관광지별 계단·쉼터 표시와 도보 시간** (가장 중요)
2. **가족이 함께 보고 의견을 맞추는 공간**, 그리고 그 의견을 반영해 일정을 다시 짜는 AI

## 2. 목표 / 하지 않는 것 / 실패 기준

### 2.1 목표 (MVP)

- 회원가입·로그인, 가족 그룹 만들기, 초대 링크로 가족 참여 **[결정]**
- 그룹 안에서 여행 일정을 만들고, 저장하고, 다시 볼 수 있음 **[결정]**
- AI로 일정 만들기 두 갈래 **[결정]**
  - A. 가지고 있는 일정을 붙여넣으면, AI가 어디를 고치고 싶은지 묻고 인터뷰를 거쳐 더 나은 일정으로 다듬음
  - B. 처음부터: 여행 스타일(여러 개 선택 + '기타' 직접 입력)과 예산을 고르고, 인터뷰를 거쳐 AI가 일정을 짬
- 인터뷰로 함께 가는 사람의 수, 각자의 나이·키·성별, 걷기 조건을 받음 **[결정]**
- 나이·키·성별과 보행 속도 연구를 바탕으로 관광지별 걷는 시간을 계산 **[결정]**
- 일정의 장소마다 가족이 반응·의견을 남기고, "의견 반영해서 다시 짜기"로 AI가 새 버전을 만듦. 버전은 모두 저장되어 비교 가능 **[결정: 의견 조율 A안]**
- 일정 화면은 가로 1:1: 왼쪽 일정·의견, 오른쪽 지도. 일정이 바뀔 때마다 바로 다시 판정하고 지도의 경로·계단·쉼터 표시를 갱신 **[결정: 지도 B안]**
- 대전의 유명 관광지 대부분에 대해 계단·쉼터·도보 시간 데이터를 갖춤 **[결정]**

### 2.2 하지 않는 것 (MVP 범위 밖)

- 대전 밖 지역 **[결정]**
- 맛집 데이터 수집 (후속 과제) **[결정]**. 식당은 일정에 넣을 수는 있지만 '장소 안 길 정보 없음'으로 다룬다
- 실서비스 수준 기능: 비밀번호 찾기, 이메일 인증, 소셜 로그인, 알림, 관리자 화면, 결제·광고 **[제안]**
- 여러 사람의 실시간 동시 편집, 실시간 반영(새로고침·주기적 갱신으로 충분) **[제안]**
- 예약 시간표 계산(이동·관람 시간이 예약 시간에 맞는지) — 노션 초안과 같음 **[제안]**
- 여행 후 구간 평가(노션 S8/F6) — 후속 과제 **[제안]**
- 모바일 앱 (웹으로만) **[결정]**

### 2.3 실패 기준 (돌아가도 실패인 경우)

- **틀린 "계단 없음".** 계단이 있는데 없다고 보여주면 서비스가 막으려던 바로 그 일이 생긴다. 데이터가 없을 때 "계단 없음"이라고 쓰지 않는다. "지도 데이터에 계단 기록 없음"처럼 근거를 붙이고, 출처·확인 날짜·신뢰 등급을 보여준다.
- **AI가 숫자를 지어내는 것.** 걷는 시간, 계단 수, 판정은 반드시 계산 엔진에서 나온다. AI가 쓰는 문장에는 계산 결과의 숫자만 넣는다.
- **부모님이 쓰기 어려운 화면.** 작은 글씨, 긴 글 입력 강요, 색으로만 구분하는 상태 표시.
- **나이로 단정하는 것.** 걷는 시간은 늘 "약 15~20분"처럼 범위와 '추정치' 표시로 보여주고, 본인이 답한 걷기 조건이 있으면 나이 기반 값보다 우선한다.

## 3. 공통 화면 원칙 (노션 1-1을 이어받음)

- 큰 글씨, 쉬운 말('무장애' 대신 '편의 시설'). 모든 화면 위에 글씨 크기 버튼(가 / 가+)
- 판정·상태는 색과 글자를 함께
- 모든 시간은 범위 + '추정치'
- 판정 근거에는 출처와 확인 날짜
- 인터뷰 답은 큰 버튼(칩) 위주, 직접 입력은 선택
- 데스크톱 기준 가로 화면. 일정 화면은 1:1 분할 **[결정]**. 좁은 화면(휴대폰)에서는 지도를 위, 일정을 아래로 쌓음 **[제안]**

## 4. 사용자와 흐름

### 4.1 사람

- **회원**: 가족 구성원 누구나 각자 계정을 만든다. 부모님도 직접 계정으로 들어와 의견을 남긴다 **[결정]**
- **그룹**: 가족 단위. 만든 사람이 그룹장. 한 사람이 여러 그룹에 속할 수 있음 **[제안]**
- **함께 가는 사람(여행자)**: 여행마다 따로 정한다. 그룹 구성원과 연결될 수도 있고, 계정이 없는 사람(예: 할머니)일 수도 있다 **[제안]**. 인터뷰에서 인원수와 각자의 나이·키·성별·걷기 조건을 받는다

### 4.2 전체 흐름

```
회원가입·로그인
  → 그룹 만들기 / 초대 링크로 참가
  → 그룹 화면(여행 목록, 구성원)
  → 새 여행
      ├─ A. 기존 일정 붙여넣기 → AI가 장소 목록으로 정리 → "어디를 고치고 싶으세요?"
      └─ B. 처음부터 → 여행 스타일·예산 고르기
     → AI 인터뷰 (함께 가는 사람, 걷기 조건, 이동수단, 시간대, 꼭 갈 곳 …)
  → 일정 화면 [왼쪽: 일정·판정·의견·버전 | 오른쪽: 지도]
      ├─ 직접 고치기 (순서·장소·시간 → 새 버전 → 자동 판정)
      ├─ 장소별 반응·의견 남기기 (가족 누구나)
      ├─ 의견 반영해서 다시 짜기 (AI → 새 버전 → 자동 판정)
      ├─ 빠른 수정안 적용 (계산 엔진 → 새 버전)
      └─ 조건 바꿔 보기 (저장 안 함, 화면에서만 다시 판정)
  → 확정 → 확정 일정 보기 · 가족에게 보내기(공유 글)
  → 그룹 화면에서 언제든 다시 보기
```

### 4.3 화면 목록 **[제안]** (경로는 빌더가 바꿔도 됨)

| 화면 | 경로 예 | 주요 내용 |
| --- | --- | --- |
| 첫 화면 | `/` | 서비스 소개, 시작하기. 시안의 3D 대전 지도 히어로 재사용 가능 |
| 가입 / 로그인 | `/signup`, `/login` | 이메일·비밀번호·이름 |
| 내 그룹 | `/groups` | 속한 그룹 목록, 새 그룹 |
| 초대 받기 | `/invite/[token]` | 그룹 이름 보여주고 참가. 로그인 안 했으면 가입·로그인 후 돌아옴 |
| 그룹 | `/groups/[id]` | 여행 목록(작성 중 / 확정), 구성원, 초대 링크 만들기 |
| 새 여행 | `/trips/new?group=` | A/B 선택 → (B) 스타일·예산 → 인터뷰 |
| 일정 | `/trips/[id]` | 1:1 분할. 아래 4.4 |
| 확정 일정 | `/trips/[id]/final` | 최종 일정, 지도, 가족에게 보내기 |

### 4.4 일정 화면 (서비스의 중심)

오하연 시안 영상의 판정 결과 화면을 기본으로 한다.

**왼쪽 (일정·조율)**
- 버전 선택(1번째 안, 2번째 안 …, 누가/AI가 만들었는지, 확정 표시)
- 판정 이유 한 문장 + 판정 배지(조건 충족 / 조정 필요 / 정보 부족)
- 요약 카드: 하루 총 걷는 시간, 가장 긴 연속 걷기 (조건 대비 ✓ / 넘어요)
- 이전 버전 대비 바뀐 점 한 줄 (예: "가장 긴 연속 걷기 27~30분 → 18~20분")
- 일정 목록: 장소마다 시간, 머무는 시간(관람 소요 시간), 걷는 시간 범위, 계단 수, 쉼터(실내/야외), 출처. 펼치면 구간별 근거
- 장소마다 반응 버튼과 한 줄 의견 (5장)
- **직접 고치기** **[결정: 왼쪽은 '일정 변경' 영역]** + **[제안: 아래 범위]**: 장소 순서 바꾸기, 장소 빼기, 장소 목록에서 더하기·바꾸기, 시간 바꾸기, 장소 사이 이동수단 바꾸기, 꼭 갈 곳·예약 표시. 고치는 동안 바로 다시 판정해서 지도·숫자가 따라 바뀌고, "저장"하면 새 버전(만든 사람 = 그 회원)이 된다. 순서가 바뀌어 새로 필요한 장소 사이 경로는 서버에서 가져온다(8.4)
- 조건 바꿔 보기(값을 바꾸면 바로 다시 판정, 저장되는 값은 아님)
- 버튼: 의견 반영해서 다시 짜기 / 빠른 수정안 보기 / 직접 고치기 / 이 안으로 확정

**오른쪽 (지도)**
- 경로선, 부담 구간 색 구분, "! 계단 24칸" 표시, 쉼터(실내/야외) 핀, 주차장·정류장 핀
- 2D/3D 전환, 구간만 보기
- 왼쪽에서 구간을 고르면 지도가 그 구간으로 이동하고, 지도에서 구간을 누르면 왼쪽 목록이 펼쳐짐 (시안 동작)
- 지도 로딩 실패 시 목록만으로 모든 정보를 볼 수 있어야 함

## 5. 의견 조율 **[결정: A안]**

- 의견은 **버전의 장소**에 붙는다.
- 반응 버튼(여러 개 가능) **[제안: 문구는 프론트가 다듬음]**: 너무 멀어요 / 계단이 걱정돼요 / 꼭 가고 싶어요 / 쉬는 곳이 더 있었으면 / 다른 곳이 좋겠어요
- 한 줄 의견(선택, 100자 정도)
- 누가 남겼는지 이름과 함께 보여줌
- 장소와 상관없는 의견(일정 전체에 대한 말)도 하나 남길 수 있음 **[제안]**
- **의견 반영해서 다시 짜기**: 그룹 구성원 누구나 누를 수 있음 **[제안]**. AI가 현재 버전 + 그 버전에 달린 의견 + 여행자 조건 + 장소 후보를 받아 새 버전을 만든다(6장). 새 버전은 이전 버전을 부모로 기록하고, 반영에 쓴 의견에는 "반영됨" 표시
- **확정**: 그룹 구성원 누구나 한 버전을 확정할 수 있고, 누가 확정했는지 보여줌. 확정을 풀고 다시 고칠 수 있음 **[제안]**
- 새 의견은 일정 화면을 열어 둔 채 몇 초~수십 초마다 다시 불러오거나 새로고침으로 보임 **[제안]**

## 6. AI

### 6.1 쓰는 곳과 안 쓰는 곳

| 쓰는 곳 | 안 쓰는 곳 |
| --- | --- |
| 인터뷰 질문 만들기·답 해석 | 걷는 시간, 계단 수, 판정, 수정안 계산 |
| 붙여넣은 일정 → 장소 목록 | 판정 이유 한 문장 (계산 결과로 만든 고정 문장) |
| 처음부터 일정 짜기 (장소 고르기·순서·시간) | 지도 경로 |
| 의견 반영해서 다시 짜기 | |
| 버전·수정안 설명 한 줄 (계산 결과 숫자만 사용) | |

### 6.2 모델과 호출

- Upstage Solar Pro 계열을 먼저 쓰고, 성능이나 요청 한도에 걸리면 opencode의 모델로 바꾼다 **[결정: 노션 'LLM API KEY']**

- 공급자를 바꿔 끼울 수 있게 AI 호출을 한 곳에 모은다. 출력은 JSON으로 받고 스키마(zod 등)로 검사, 실패 시 한 번 다시 요청 **[제안]**

### 6.3 인터뷰 **[제안]**

인터뷰는 "AI가 자유롭게 대화"가 아니라 **채워야 할 칸이 정해진 대화**다. AI는 질문을 자연스럽게 말하고, 자유 입력 답을 칸 값으로 바꾸고, 필요한 경우만 덧붙여 묻는다. 화면에는 질문마다 큰 선택 버튼 + 직접 입력.

채울 칸:

| 칸 | 내용 | 비고 |
| --- | --- | --- |
| 함께 가는 사람 | 인원, 각자 이름/관계(엄마·아빠·나 …), 나이, 키, 성별 | 그룹 구성원 정보가 있으면 미리 채움. 인터뷰는 여행을 만드는 사람이 진행하고, 부모님 칸은 대신 답하거나 "부모님께 직접 받기"로 비워 둘 수 있음 → 아래 '여행자 정보 고치기' |
| 걷기 조건 (사람마다) | 쉬지 않고 걷기, 하루 총 걷기, 한 번 쉬는 시간, 계단 피하기, 걷는 속도(천천히/보통), 보행 보조기구 사용 | 질문마다 '잘 모르겠어요' 가능 → 기본값. 시안 `plan-data.ts`의 생활 예시 선택지 재사용 |
| 날짜·시간대 | 여행 날짜(하루), 출발·귀가 희망 시간 | |
| 이동수단 | 자가용 / 대중교통 / 택시 | 장소 사이 이동과 출발 지점(주차장 또는 정류장) 결정에 씀 |
| 여행 스타일 (B) | 관광·명소, 레저·체험, 휴식·힐링, 자연·산책, 맛집·음식, 문화·역사, 과학·전시, 온천·스파, 사진 명소, 쇼핑 + 기타 직접 입력 | 관광·레저·휴식은 [결정], 나머지는 [제안] |
| 예산 (B) | 1인당 하루: ~3만 / 3~5만 / 5~10만 / 10만 원~ | 구간은 [제안] |
| 꼭 갈 곳 / 예약 | 장소, 예약 시간 | 수정·다시 짜기에서 빼거나 바꾸지 않음 |
| 고치고 싶은 곳 (A) | 붙여넣은 일정 중 어디가 불만인지 | A 갈래에서만 |

**여행자 정보 고치기** **[제안]**: 인터뷰가 끝난 뒤에도 그룹 구성원 누구나 여행의 '함께 가는 사람' 정보(나이·키·성별·걷기 조건)를 고칠 수 있다. 계정과 연결된 여행자(예: 엄마 계정)는 본인이 직접 자기 걷기 조건을 채울 수 있고, 부모님이 직접 고른 값이 있으면 그 값을 쓴다(노션의 '부모님이 직접 고른다' 원칙). 조건이 바뀌면 모든 버전은 **열 때 현재 조건으로 다시 판정**한다. 버전에 저장된 판정 요약은 목록 표시용일 뿐이고, 조건이 바뀌면 다시 계산해 덮어쓴다.

### 6.4 일정 만들기·다시 짜기 규칙 **[제안]**

- AI는 **우리 장소 DB 안에서만** 관광지를 고른다. 서버가 스타일·예산·이동수단·걷기 조건(예: 계단 피하기면 계단 많은 곳 뒤로)으로 후보를 추려서 넘기고, AI는 장소 id로 답한다. 목록에 없는 이름이 오면 버린다.
- 식사 자리처럼 DB에 없는 장소는 "점심(둔산동)" 같은 이름만 있는 자리로 넣을 수 있다 → 판정에서 '장소 안 길 정보 없음'.
- AI가 만든 일정은 바로 계산 엔진으로 판정한다. **조정 필요**면 위반 내용을 붙여 AI에게 한 번 더 고치게 한다(최대 1회). 그래도 안 되면 그대로 보여주고 빠른 수정안을 안내.
- 붙여넣은 일정(A)의 장소 이름은 AI가 장소 DB와 맞추고, 못 맞춘 이름은 장소 검색(TMAP POI)으로 좌표만 찾아 '정보 없음' 장소로 둔다.
- AI 실패 시: A는 장소를 직접 고르는 화면, B는 "다시 시도" + 장소 직접 고르기.

## 7. 보행 계산 엔진

노션 4장의 판정 규칙과 시안 코드 `Bopok/src/lib/judge.ts`를 출발점으로 한다. **순수 TypeScript 모듈**(React·DB 의존 없음)로 만들어 브라우저(즉시 다시 판정)와 서버(버전 저장 시 요약 저장)에서 똑같이 쓴다. **[제안]**

### 7.1 걷는 속도 모델 **[결정: 나이·키·성별 기반] + [제안: 아래 구체 규칙]**

여행자 한 명의 속도(m/s):

1. **기본값 = 나이대·성별 속도**: Andrews 외 2023 메타분석(성인 51,248명, 편한 속도, cm/s). 노션 보행 속도 조사 3.1에서 권고한 기본값

   | 나이 | 여 | 남 |
   | --- | --- | --- |
   | 18~29 | 138 | 136 |
   | 30~39 | 138 | 139 |
   | 40~49 | 134 | 140 |
   | 50~59 | 125 | 134 |
   | 60~69 | 121 | 126 |
   | 70~79 | 113 | 120 |
   | 80+ | 97 | 105 |

   18세 미만은 노션 조사 4.3의 아동 값으로 [빌더].
2. **키 보정**: 키 10 cm마다 ±0.07 m/s (Pua 외 2022). 기준 키와 보정 상한은 [빌더] (제안: 여 158 cm, 남 171 cm 기준, ±0.10 m/s 상한)
3. **본인 답이 우선**: '천천히 걸어요'면 0.85 m/s 이하로 (한음 외 2020, 한국 고령 보행자 하위 15%), 보행 보조기구 사용이면 0.73 m/s 이하로 (같은 논문, 지팡이·휠체어 사용 고령자)
4. **일행 속도 = 함께 가는 사람 중 가장 느린 사람**, 걷기 조건(쉬지 않고 걷기·하루 총·계단 피하기)도 가장 엄격한 사람 기준

모든 상수는 한 파일에 모으고 상수마다 출처를 주석으로 단다. 연구 값은 4~10 m 실험실 측정이라 실제 길보다 빠르다는 한계가 있음(노션 조사 4.7) → 여유율로 보완.

### 7.2 구간 하나의 걷는 시간

```
걷는 시간(분) = 거리(m) ÷ (속도(m/s) × 60) × 계단 가중치 × 경사 가중치
범위 = [걷는 시간, 걷는 시간 × (1 + 여유율)]
```

- 계단 가중치 2.0, 경사 가중치 1.5: 시안 코드 값, 근거 없음 → 임시값으로 두고 근거 찾으면 교체 **[빌더]**
- 여유율: 초기값 0.2 **[제안]** (시안은 0.1. 개인차가 크다는 조사 결과를 반영해 넓힘)
- 조건 비교는 범위의 최댓값으로 (부모님 쪽으로 안전하게) — 노션과 같음

### 7.3 판정 순서

1. 하루 경로 이어 붙이기: 첫 장소의 출발 지점(이동수단에 따라 주차장 또는 정류장)부터 일정 순서대로 "장소 안 관람 경로 → 다음 장소까지 가는 길". 빼기로 한 구간은 빼고, 우회로로 바꾼 구간은 바꿈
2. 연속 걷기 묶음 만들기: 아래에서 끊긴다 **[제안]**
   - 쉬기로 한 쉼터
   - 탈것 구간(자가용·택시·버스)
   - 앉아서 머무는 장소(식사, 카페, 족욕 등 `seated` 표시된 장소)
   - 관람형 장소 사이를 걸어서 이동하면 **이어진다** (노션 예시 "한밭수목원에서 국립중앙과학관까지 쉬지 않고 약 28분"과 같음. 시안 코드는 장소마다 끊었는데 이 규칙으로 바꿈)
3. 위반 검사: 가장 긴 연속 걷기 > 쉬지 않고 걷기 조건 / 하루 총 > 하루 총 조건 / 계단 피하기인데 계단 구간 존재
4. 결과: 위반 있음 → 조정 필요, 위반 없고 정보 없는 장소 있음 → 정보 부족, 그 외 → 조건 충족
5. 판정 이유 한 문장: 노션 4-2 규칙 그대로(계단 먼저, 없으면 가장 많이 넘은 위반, 장소 이름과 숫자)
6. 부분 판정: 정보 없는 장소는 안쪽을 빼고 장소 사이 이동만 판정 (노션 4-4). 이번에는 우선순위 1 — AI 추천에 식당이 자주 들어가기 때문 **[제안]**

머무는 시간(관람 소요 시간)은 일정표 표시용이고 걷는 시간 합계에는 넣지 않는다.

### 7.3.1 장소 안 경로와 장소 사이 이동 **[제안]**

- **출발 지점은 이동수단에 따라 다르다.** 장소마다 출발 지점을 둘 이상 가질 수 있다: 주차장(자가용·택시 하차), 정류장(대중교통). 그 장소에 들어올 때 쓴 이동수단에 맞는 출발 지점에서 장소 안 경로가 시작된다.
- **장소 안 경로**: 출발 지점 → 입구 → 볼거리들(순서대로) → 나가는 지점.
  - 다음 이동이 **탈것**(자가용·택시·버스)이면 나가는 지점에서 **다시 출발 지점(주차장·정류장)까지 걸어 돌아가는 구간을 센다**. 시안은 들어가는 길만 셌는데, 돌아 나오는 길도 부모님이 걷는 길이다.
  - 다음 이동이 **걷기**면 마지막 볼거리(또는 지정된 출구)에서 바로 다음 장소로 걸어간다.
  - 장소 안 구간 데이터(8.4)는 이 왕복을 계산할 수 있게 "출발 지점 ↔ 입구"와 "볼거리 사이" 구간을 저장한다. 돌아가는 길은 같은 구간을 거꾸로 쓴다(계단·경사도 같다고 봄).
- **장소 사이 이동수단(`arriveBy`) 정하기**:
  - 기본값은 인터뷰에서 고른 이동수단: 자가용 → 모두 자가용, 택시 → 모두 택시, 대중교통 → 700 m 이하는 걷기, 그보다 멀면 버스
  - AI가 일정을 짤 때와 사용자가 직접 고칠 때 장소 사이마다 바꿀 수 있다
  - 빠른 수정안 C는 걷는 장소 사이 구간을 택시로 바꾼다
- **대중교통**: MVP에서는 대중교통 경로 API를 쓰지 않는다. 버스 구간은 탈것 구간으로 보고 시간은 거리로 대략 추정(표시용)하고, 부모님이 실제로 걷는 부분인 **정류장 ↔ 입구** 걷기는 장소의 정류장 출발 지점으로 정확히 센다. 정류장에서 갈아타는 걷기는 세지 않는다는 한계를 화면에 "버스 갈아타는 길은 포함 안 됨"으로 적는다. 대중교통 API(TMAP 대중교통, ODsay 등)는 후속 과제.

### 7.4 빠른 수정안 **[제안]**

노션 4-3의 A·B·C를 계산 엔진으로 유지한다. 적용하면 새 버전이 된다.

- A 동선 조정: 계단 구간 → 우회로, '선택' 구간 빼기
- B 휴식 추가: A + 가장 긴 묶음 중간 쉼터에서 쉬기
- C 이동수단 변경: B + 장소 사이를 택시로
- 장소 빼기·바꾸기는 계산 엔진이 아니라 "의견 반영해서 다시 짜기"(AI)가 맡는다
- 카드마다 바뀐 점 한 줄은 AI가 쓰되, 실패하면 고정 문장 (노션과 같음)

### 8.3 계단 판정 방법

TMAP의 '계단 제외' 옵션은 노션 테스트에서 일반 경로와 같은 결과를 냈으므로 믿지 않는다. 대신 **TMAP 경로선과 OSM 계단 선이 겹치는지 직접 검사**한다(경로를 몇 m 폭으로 넓혀 교차 검사, 폭은 [빌더]). OSM에 `step_count`가 있으면 칸 수로, 없으면 "계단 있음(칸 수 모름)". 홈페이지·현장 확인 값이 있으면 그 값이 우선.

**구간마다 계단 상태는 세 가지** **[제안: 세 상태] + [결정: '기록 없음'은 느슨하게]**

| 상태 | 언제 | 화면 표시 | 판정 |
| --- | --- | --- | --- |
| 계단 있음 | OSM 겹침, 또는 홈페이지·안내도·로드뷰로 확인 | "! 계단 24칸" | 계단 피하기면 위반 |
| 계단 없음 확인 | 데이터 작업자가 안내도·로드뷰 등으로 직접 확인 | "계단 없음 (확인 2026-11, 안내도)" | 위반 아님 |
| 기록 없음 | 아무도 확인 안 했고 OSM에도 없음 | "계단 기록 없음 (지도 데이터 기준)" | **위반 아님.** '조건 충족'이 될 수 있다. 대신 계단 피하기를 켠 여행이면 판정 배지 아래에 "계단 기록이 없는 구간 n곳 · 지도 데이터 기준"을 항상 함께 보여주고, 누르면 그 구간들이 목록·지도에 표시된다 |

'계단 없음'이라고 단정하는 문장은 '계단 없음 확인' 상태에서만 쓴다. 유명 관광지의 장소 안 구간은 데이터 작업(P5) 때 사람이 '있음' 또는 '없음 확인'으로 채워서, 중요한 구간에 '기록 없음'이 남지 않게 하는 것을 목표로 한다. '기록 없음'은 주로 장소 사이 길(인도)과 정보 없는 장소에서 생긴다.

### 8.4 미리 계산 vs 그때그때

- **장소 안 구간**: 데이터 작업 스크립트로 미리 계산해서 DB에 넣는다(사람이 입력한 지점 → TMAP 경로 → 계단 겹침 검사 → 구간). 우회로가 있으면 우회로 구간도 함께
- **장소 사이 구간**: 일정 순서에 따라 달라지므로 필요할 때 서버에서 TMAP 호출 → 결과 저장(같은 두 지점은 재사용)
- 모든 값에 출처, 확인 날짜, 신뢰 등급(A 공식 안내·현장 확인 / B 지도에서 측정 / C 사진·후기로 추정)

### 8.5 데이터 모양 (시안 코드에서 이어받음)

시안의 `Segment`(거리·계단·경사·쉼터·우회로·출처), `GeoNode`(start/entrance/sight/rest/toilet, 실내/야외), `SegmentGeo`(좌표 경로) 구조를 DB 테이블로 옮긴다(10장).

## 9. 지도

- MapLibre GL + OpenFreeMap 배경 지도 **[결정]**. 바뀔 수 있음 → 지도 라이브러리를 부르는 코드는 지도 컴포넌트 한 곳에만 두고, 나머지는 "경로 GeoJSON, 핀 목록, 맞출 범위, 2D/3D" 같은 값만 넘긴다 **[제안]**

- 지도 저작권 표기(OSM, OpenFreeMap) 유지

### 10.2.1 한 레포 안에서 프론트·백엔드 나누기 **[제안]**

Next.js App Router에서 `app/` 아래 폴더 하나는 주소 하나다. 그 폴더의 `page.tsx`는 **화면**, `route.ts`는 **API**가 된다. 화면 하나를 그리는 코드나 서버 로직은 `app/` 밖(`components/`, `lib/`)에 몇 개의 파일로든 나눠 둘 수 있다. 그래서 한 레포 안에서 폴더 단위로 담당을 나눈다.

| 폴더 | 담당 |
| --- | --- |
| `app/**/page.tsx`, `app/**/layout.tsx`, `components/**`, `public/**` | 프론트 (오하연) |
| `app/api/**/route.ts` | 해당 기능 파트 (예: `app/api/groups/**` → P1) |
| `lib/contracts/**` | 프론트 + 백엔드 함께 (바꿀 때 서로 리뷰) |
| `lib/db`, `lib/auth` | P1 (스키마는 파트별로 파일을 나눔) |
| `lib/ai` | P3 |
| `lib/engine`, `lib/geo` | P4 |
| `scripts/data`, `data/` | P5 |

- 프론트와 백엔드의 경계는 **`app/api/**/route.ts`(Route Handler)** 로 둔다. Server Action은 컴포넌트가 서버 함수를 직접 부르는 방식이라 경계가 흐려지므로, 폼 제출처럼 한 화면에서만 쓰는 곳에 한정한다.
- 요청·응답 모양은 `lib/contracts`에 타입과 스키마로 먼저 정하고, 프론트는 API가 완성되기 전까지 같은 모양의 목업으로 개발한다.
- `lib/engine`은 브라우저에서도 import하므로 DB·키 같은 서버 전용 코드를 넣지 않는다. 서버 전용 모듈은 `server-only`로 표시한다.
- 별도의 백엔드 서버(Express, FastAPI 등)는 두지 않는다. 배포가 하나로 끝나고, 프론트·백엔드가 타입을 그대로 공유할 수 있다. 오래 걸리는 데이터 작업은 배포 서버가 아니라 `scripts/`로 로컬에서 돌린다.
