현재 VS Code에 열려 있는 보폭 저장소에서 실제 구현과 로컬 검증을 진행해 주세요. 추가 관광정보 수집은 이번 범위에서 제외합니다. 이 문서는 조사자료 핸드오프이며, 현재 코드·DB에 이미 적용됐다는 뜻이 아닙니다.

## 2. 현재 저장소를 먼저 점검
1) 저장소 작업규칙(AGENTS.md 등), package.json, DB 스키마·연결·마이그레이션, seed/import 도구, 장소/경로 API, 프론트 데이터 어댑터·타입·테스트를 실제로 읽으세요. 과거 설명으로 파일명·테이블명·브랜치·병합 상태를 추정하지 마세요.
2) git branch --show-current, git status --short, git diff --stat를 확인해 기존 작업과 이번 변경을 구분하세요. 사용자 변경을 덮어쓰거나 reset/stash/switch/pull/commit/push/merge하지 마세요. 충돌이 예상되면 필요한 부분만 질문하세요.
3) 기존 패키지매니저와 관례를 따르고 불필요한 의존성·프레임워크 교체는 하지 마세요.
4) API키는 제공하지 않았으며 오프라인 자료 반영에는 새 관광API 호출이 필요 없습니다. .env 등의 비밀값을 출력·복사·커밋하지 마세요.
5) 원본·대용량 연구자료를 프런트 번들이나 Git에 무조건 포함하지 마세요. 기존 정책과 .gitignore를 확인해 로컬 입력자료와 실제 배포/테스트에 필요한 최소 자료를 분리하세요. 원본 파일은 수정하지 마세요.

## 3. 매핑 설계와 데이터 해석 원칙
먼저 현재 스키마와 JSON 필드를 대조한 간단한 매핑표를 만들고 필요한 최소 변경을 제시하세요. 저장소가 지원하는 구조를 우선 재사용하세요.

- places가108개 후보의 진입점입니다. accessibilityApiAll186이나 raw의 대전844건을 전부 앱 관광지로 넣지 마세요.
- DJ-001 같은 조사ID와 F-00001 같은 근거ID는 현재 DB의 PK가 아닙니다. 자료 버전/네임스페이스를 포함한 외부ID 매핑을 보존하세요. 이 순번ID가 다른 수집버전에서도 의미가 같다고 가정하지 마세요.
- 동일 시설, 부분시설, 연구원과 내부 박물관, 회덕향교와 대성전 같은 중첩을 검토하세요. 108행을 무조건108개 독립 장소로 만들거나, 반대로 이름만 보고 합치지 마세요. 전체108후보의 처리결과와 기존/신규 DB ID 매핑을 남기세요. 합친다면 근거와 부모/자식·구간 범위를 보존하세요.
- tourApiMatch.matchKind의 exact_name/alias_address와 subsite_only/superset_only/no_match를 구분하세요. 관련 콘텐츠의 주소·좌표·시설속성을 전체 관광지의 확정값으로 옮기지 마세요.
- 장소, 건물/구간, 출처와 관찰근거, 사진권리, 조회상태를 구분하세요. scope, direction, numericValue, unit, sourceDate/providerUpdatedAt, observedAt, reviewStatus, caveat를 잃지 마세요. 조회일을 현장 측정일이나 편의시설 수정일로 바꾸지 마세요.
- sourceChecks는 자료원 조회상태이지 물리적 시설 정보가 아닙니다. 1707개 기록에는 요약·운영정보·관련자료도 있으므로 모두 계측된 이동수치로 취급하지 마세요.
- valueRepresentation/sourceType을 참고해 수집자 요약과 API 원필드를 구분하세요. 웹/파일 요약을 축어 인용으로 표시하지 마세요. HTML은 그대로 실행/삽입하지 말고 기존 안전한 텍스트 처리나 sanitizer를 사용하세요.
- excludeFromPlaceSummary=true 또는 quarantined에 해당하는39건은 사용자용 확정 요약, 추천·접근성 계산에서 제외하세요. 별도 검토근거로 보존하는 것은 가능합니다. eligibleForScopedSummary는 적용범위를 지킨 문장표시 허용일 뿐 접근 안전 보증이 아닙니다.
- null, 빈값, 미기재, 미매핑, 미실조회를 false/0/없음/접근가능으로 자동 변환하지 마세요. 모든 장소의 continuousWheelchairAccess는 전체범위 unverified이고 fieldVerified/currentFieldVerified도 현장검증 완료가 아닙니다.
- 무장애 API의 wheelchair는 휠체어 대여, exit는 주출입구, route는 원문이 정한 접근구간 정보입니다. 대여 가능이나 입구 무단차를 전체 연속 무장애 동선으로 바꾸지 마세요.
- 주차대수는 주차장~입구 거리가 아니고 구조물 폭은 보행 유효폭이 아닙니다. 단위 오류·상이한 기종점·충돌값은 임의 정정·평균·합산하지 마세요. conflicts/gaps를 보존하세요.
- location은 대표점이며 입구가 아닙니다. 경도/위도 순서와 값 범위를 검증하고, 부분시설/상위권역·주소건물·경계꼭짓점을 전체 관광지의 정확한 입구로 쓰지 마세요. 좌표가 없는 곳에 0,0·동일 임의좌표·추정 입구를 넣지 마세요. 현재 스키마가 좌표 필수라면 미확보 후보는 staging/pending 목록 등으로 보존하고 제외 이유를 보고하세요.
- OSM properties.placeIds와 relationToSites/relationToSite를 함께 보세요. bbox_only 등의 주변객체를 내부시설로 일반화하지 마세요. steps 선분수는 실물 계단 개수가 아니며 length_m은 좌표로 계산한2D선분길이이지 코스 총거리나 주차장~입구 경로거리가 아닙니다.
- OSM은 이번에는 출처가 있는 후보 레이어/근거로 보존하세요. 연결·스냅·통행 검증 없이 기존 경로엔진의 확정 네트워크로 주입하거나 비용/추천 알고리즘을 바꾸지 마세요.
- 2017 수통골 좌표묶음은 현행 GPX 검증본이 아닙니다. 고도·공원경계 없음, 숫자 난이도 해석·CRS 정의 미확인입니다. 과거 통제값·CSV 시간0을 현재 개방·실제0분으로 판정하지 마세요.
- 사진은 URL·권리코드 자료입니다. 권리·출처를 보존하고 허용조건 확인 전 무조건 공개하지 마세요. OSM 출처표시/ODbL과 다른 공공자료 이용조건을 분리해 관리하세요.

## 4. 실제 구현 범위
1) JSON/GeoJSON 입력 검증과 후보ID→DB ID 매핑을 구현하세요. 중복·제외·보류·좌표미확보·부분시설 처리 내역을 기계 판독 가능한 보고서로 만드세요.
2) 재실행해도 중복 증가가 없는 importer/upsert를 구현하세요. 근거·이미지·OSM 객체에도 적절한 유일성 키가 필요합니다. 전체 삭제 후 재삽입 방식은 쓰지 마세요. 기존 seed가 전체 삭제를 한다면 그대로 실행하지 마세요.
3) 쓰기 없는 dry-run이 추가/갱신/중복/통합/보류/제외/미확인 건수와 오류를 보여주게 하세요. 데이터 오류를 조용히 무시하지 말고 원본ID·필드·사유를 남기세요.
4) DB 쓰기는 확인된 로컬/테스트 DB에만 하세요. 현재 DB 방식에 맞는 백업·트랜잭션·롤백 절차를 준비하세요. 운영/공유 DB이거나 대상이 불분명하면 쓰기 전에 승인을 받으세요.
5) 스키마 변경이 필요하면 최소 변경으로 migration을 생성하고 SQL을 검토하세요. 특히 Drizzle이라면 스키마 export/등록을 확인하고, 의도하지 않은 DROP/TRUNCATE/데이터 손실 SQL은 적용하지 마세요. 운영 migration은 자동 적용하지 마세요.
6) 확인된 로컬/테스트 환경에서는 계획만 제시하고 끝내지 말고 구현·dry-run·적용·재실행 검증까지 진행하세요. 환경 제약은 정확한 미완료 범위와 최소 다음 조치로 보고하세요.
7) 기존 장소 목록/상세 API 계약을 가능한 한 유지하며 새 데이터가 조회되도록 연결하세요. 기존 프론트 어댑터/타입과 연결해 목록·상세·지도표시 및 출처·미확인 안내를 검증하세요. 임의 API를 새로 가정하거나 실제 DB 대신 임시 배열만 보여주는 것으로 끝내지 마세요.
8) 추가 OSM19곳 조사, 새 API신청, 현장조사, 전체 경로엔진 재설계는 하지 마세요. 이번 목표는 확보한 자료를 안전하게 기존 서비스에 반영하는 것입니다.
